# 2026.260.1947 — fix(entity): resolve a kind:pipeline entity from imported/discovered docs

## Summary

`charly pipeline run|validate <entity>` could not resolve a `kind:pipeline` entity that lives in
a flat `import:` sibling file (the documented per-kind split, e.g. `- pipelines.yml`) or a
`discover:`d manifest — even though the host loader accepts and validates exactly those documents
(`charly box validate` schema-checks a malformed *imported* pipeline entity).

### RCA (R1)

`command:pipeline` is a **baked** command plugin: charly's command dispatch `syscall.Exec`s the
plugin binary in CLI mode (`sdk.Main`, `IsServeMode false`), so there is **no go-plugin broker
and no reverse-channel executor** — the plugin cannot call the host loader (documented in-tree,
`ade.go` "why NOT in-plugin dial dispatch").

- `ade.go`'s `findBedEntity` already solved this class for beds — a by-name search.
- `entity.go`'s `loadEntity` was the inconsistent sibling: it read **only**
  `<projectDir>/charly.yml`, so an entity in an imported/discovered document was invisible.

```
$ charly box validate                       # OK — the imported pipeline entity validates
$ charly pipeline validate eval-pr-plan
pipeline: pipeline entity "eval-pr-plan" not found in charly.yml
```

### Fix

Re-derive the same resolution from the filesystem, following the project's OWN `import:` /
`discover:` directives (root-wins), using the canonical spec decoders so the grammar is never
forked (R3): `spec.ImportList`, `spec.DiscoverConfig`, and `specloader.FindEntityDirs`. ONE shared
resolver (`entityDocs` + a per-document walk) backs BOTH `loadEntity` and `findBedEntity`, so bed
and pipeline resolution cannot drift.

**Error discipline (R1):** a read/parse/scan failure on a document the resolver was *instructed*
to read (the root, an `import:` sibling, a `discover:`d manifest) is propagated and named — never
silently skipped. A malformed root/sibling or a missing import path surfaces its real cause, not
"entity not found"; a name present under a *different* kind is diagnosed as such.

**disposable** fixture (committed below inline) exercises BOTH changed resolver paths in ONE run,

  `loadEntity` (no root `charly.yml` copy);
