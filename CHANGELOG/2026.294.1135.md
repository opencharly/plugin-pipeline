# 2026.294.1135 — fix(args): widen the workflow arg maps to map[string]any, on the sdk/spec lanes releases

## Summary

Leg 4 of the chain in `plugin-pipeline#43`: the workflow front-end takes the arg widening leg 1
landed (`spec#262`) and the sdk release that carries the `lanes` gate (`sdk#440`) — the last
front-end blocker between the engine's `lanes:` arm and a green `check-lobster-local` in
`plugin-lobster`.

**Why the widening was always owed.** `spec#262` widened the four workflow arg maps —
`#WorkflowRunRequest.args`, `#WorkflowSchedule.args`, `#PipelineSchedule.args`,
`#PipelineArms.workflow_args` — from `#StrVal` to `#WorkflowArgVal: #StrVal | [...#StrVal]`, so a
runtime LIST can cross the engine wire. This repo was pinned at `sdk v0.2026293.2302` /
`spec v0.2026289.611`, BELOW the widening, so its arg path never had to face it. The pin pair the
`lanes` gate requires — `sdk v0.2026294.1003` / `spec v0.2026294.929` — forces it, and on the
untouched base tree the pin bump alone is a compile error:

```
$ go mod edit -require=github.com/opencharly/sdk@v0.2026294.1003 -require=github.com/opencharly/spec@v0.2026294.929 ; go mod tidy ; echo "tidy rc=$?"
tidy rc=0

$ go build ./... ; echo "rc=$?"
# github.com/opencharly/plugin-pipeline/candy/plugin-pipeline
./cli.go:336:77: cannot use args (variable of type map[string]string) as map[string]any value in struct literal
rc=1
```

That break is filed as `plugin-pipeline#46`.

**The widening: 4 files, +124 / -20.**

- `candy/plugin-pipeline/cli.go` (37/9) — `runDispatchFlags` returns `map[string]any`, and
  `var args map[string]string` at `cli.go:345` becomes `map[string]any`. The two `--args-json` error
  texts (`cli.go:349`, `:352`) stop demanding STRING values. A new `workflowArgValue` admits exactly
  what `#WorkflowArgVal` admits — a STRING, or a FLAT LIST of STRINGs — and keeps a NAMED error for
  what the wire does not admit (object, boolean, number, null, a list nested in a list), because the
  lowering emits `-p NAME="$NAME"` for every declared arg and a dropped arg must never become a
  silently-empty one. The `--args-json` doc comment above `workflowRunParams` claimed the envelope
  field was `map[string]string`; it now states the admitted shape.
- `candy/plugin-pipeline/cli_workflow_test.go` (81/5) — the widening's locks: a scalar-only args
  document round-trips through `spec.WorkflowRunRequest` byte-identically, a flat list crosses as a
  list in item order, the CLI accepts a list before the executor check, and the reject table gains
  the four shapes the widening still refuses.
- `candy/plugin-pipeline/go.mod` (2/2) + `candy/plugin-pipeline/go.sum` (4/4) — `sdk v0.2026294.1003`
  and `spec v0.2026294.929`, and only those hashes. No other dependency moves.

**`entity.go:213` / `plugin.go:106` need nothing — verified, not assumed.** Both are
`workflowkit.ValidatePipeline` call sites. The module compiles unchanged against the new pin (the
`go build` block below), and the gate they call admits `lanes`: `sdk/workflowkit/validate.go:238`
carries the pool-width rule, and the chain-closing run below drives that same gate through the
authored path, where it refuses a `lanes:` step with no `batch_size` and accepts one that has it.
Neither file is in the diff.

**Chain-closing answer: yes — with this front-end the lane arm is admitted AND run.** With the
front-end built from this tree, `plugin-lobster`'s `check-lobster-local` runs the `lanes:` step
handed over on `plugin-lobster#7`: `13 steps: 13 passed, 0 failed, 0 skipped`, `[lobster-lanes]`
`exit=0`, `errors: 0`, `warnings: 0`, `ok: true`. The control is the SAME bed on the SAME engine
with the front-end built from `origin/main` (`7b90340`): `13 steps: 12 passed, 1 failed`,
`[lobster-lanes]` `exit=1, want 0`, because the gate refuses the arm outright with
`step "lane": no execution arm`. The front-end was the blocker and it no longer is. What remains is
sequencing in `plugin-lobster`: `#10` carries the engine arm and `#7` carries the bed step; the step
was inserted in a throwaway clone at `ac27b32` (the `#10` head) for these runs, and nothing was
pushed to that repo.
