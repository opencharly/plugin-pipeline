**Stated honestly — and this is a finding this PR surfaced rather than fixed:** this repo's committed projection is **NOT** what the named command produces. `charly candy params plugin-pipeline --check` reports it **STALE** (exit 1), and the difference is exactly the tag-normalization step — the committed file carries `json:"type"`, the canonical pipeline produces `yaml:"type,omitempty" json:"type"`. Every other committed `cue_types_gen.go` in the org carries the yaml tags; this repo's `ci.yml` reproduces the json-only form because its recipe omits that step.

That is filed as **opencharly/plugin-pipeline#35**, with the measurement and the two ways to settle it — because it is a contract decision, not a docs edit:
- this repo's schema compensates deliberately (its snake_case keys are paired with Go field names chosen so yaml.v3's lowercasing lands on the same key — `@go(Max_retries,optional=nillable)` exists for exactly that), so json-only tags may be load-bearing here; and
- regenerating the artifact without also re-keying that repo's CI (which cannot obtain charly yet: `go install github.com/opencharly/charly/charly@v2026.280.2217` fails, "does not contain package …") would simply turn its own gate red.

So the README names the command that regenerates the file **and** the `--check` gate (both true and actionable: a reader who runs `--check` today gets a red gate whose message names this repo's divergence — the gate working, not a false positive), while the artifact itself is untouched by this PR, because aligning it is the decision #35 asks for rather than a docs edit. The command itself was proven live in its own PR (opencharly/plugin-candy#9: four arms through a freshly rebuilt dev binary with `cue` absent from `PATH`).
