# 2026.252.2149 — fix(pipeline): per-run lane state — the batch lanes raced package globals

## Summary

The eval-lane batch mode (`pipeline run --prs a b c --lanes N`) was unusable under concurrency: 12/12 lanes died at bed-render with empty triage plans while single-PR runs were fine. This PR makes every piece of per-run state per-run, replaces the hand-rolled `exec.Command("gh")` subprocesses with the NEW canonical ghkit client (github.com/opencharly/plugin-gh), and makes the probe + ledger layers run-context-aware.

## The RCA (each step from live evidence)

1. The 404 mystery: prTool assigned `prRef`'s `(pr, repo)` SWAPPED — the URL was `/repos/10144/pulls/omacom/omarchy` (a repo literally named 10144) → 404. Found via the instrumented run transcripts.
2. The env race class: `runBatch` `os.Setenv` per lane, the package-global `curLedger`, `EVAL_MAX_TURNS`, `EVAL_PR_NUMBER` in probeMediaGate — ALL process-global state written by concurrent lanes → replaced by per-run state in `runCtx`.
3. The executor-env boundary: the plugin serve subprocess does not see the operator's shell env — the repo now comes from the ENTITY (`#PipelineInput.repo`); ghkit's token contract is explicit (GH_TOKEN → GITHUB_TOKEN → the gh hosts.yml), the base URL is pinned, and every non-2xx surfaces status + body.
4. Dead surfaces discovered: the ledger tools (stage_output/read_summary) had no dispatcher and empty param schemas; extractJSON truncated any value with a comma — all fixed, all runCtx-aware.
